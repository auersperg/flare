# Задание агенту: минимальное расширение Flare — поиск по материалам и MCP

Дата: 2 ноября 2026 года.

## 1. Задача

Нужно расширить **инфраструктуру Flare**, чтобы на ней можно было создать приложение с полноценными кейсами, документами, историей, задачами и работой нескольких разрешённых агентов.

**Flare остаётся бэкендом.** Не превращать его в систему ведения дел, аналог Mem0 или собственный агентный фреймворк. Предметные сущности и правила памяти принадлежат будущему приложению.

Минимальный целевой объём первой версии:

1. Поиск по явно выбранным файлам приложения.
2. Безопасный доступ внешних агентов к явно выбранным функциям приложения через MCP.
3. Небольшая вкладка AI в существующей панели.
4. Соответствующие серверные возможности и публичный SDK — не только интерфейс.

Модель уже есть у внешнего агента. Собственная генерация ответов внутри Flare не является обязательной частью этой версии. Использование моделей для индексации поисковым сервисом — другой вопрос, оно может быть частью работы поиска.

## 4. Поиск по материалам

Выбранное направление — **Cloudflare AI Search через нативный instance binding в Runtime** и Items API. Установленные Wrangler/types уже содержат `ai_search` и Items API; это подтверждает наличие контракта, но не облачную работоспособность.

- Подключать существующий выделенный instance к конкретному `project/environment` через operator config. Для первой версии — разные instances для разных сред, без общего индекса с одним клиентским фильтром. Не создавать instance на каждый кейс/пользователя и не выдавать приложению namespace/account API.
- По умолчанию Search выключен. Не создавать облачные ресурсы при обычном deploy приложения. Создание instance требует отдельного согласования; подключение должно проходить через managed config.
- Items API загружает явно выбранные файлы во [встроенное хранилище AI Search](https://developers.cloudflare.com/ai-search/configuration/data-source/built-in-storage/). Это управляемая производная копия, **не** подключение всего общего `FILES` bucket и не второй собственный storage/index pipeline. Оригинал остаётся в Flare/R2.
- Raw search вызывается через [search API](https://developers.cloudflare.com/ai-search/api/search/workers-binding/), без chat completions. Не открывать прямой публичный Search/MCP endpoint провайдера в обход ACL приложения.

### Минимальные возможности

- Приложение явно выбирает файлы для индексации. Не индексировать автоматически весь общий R2 bucket.
- Поисковая запись связана с immutable file ID, scope и фактической идентичностью R2-объекта; ключ загрузки детерминирован, без пользовательского имени как уникального идентификатора. Повтор отправки того же файла должен восстанавливать ту же запись, включая сбой после загрузки до сохранения ответа.
- Разделять локальное желаемое состояние (включён/исключён/ожидает отправки) и состояние провайдера. [Items API](https://developers.cloudflare.com/ai-search/api/items/workers-binding/) возвращает `queued`, `running`, `completed`, `error`, `skipped`, `outdated`; успешный upload ещё не означает готовность. Не превращать `skipped` без причины в «неподдерживаемый формат», а неизвестный статус — в успех.
- Серверные функции приложения могут выполнять поиск с разрешёнными фильтрами.
- Результат содержит file ID, доступный фрагмент и сведения об источнике. Страницу/позицию возвращать только когда они действительно известны.
- Предусмотрены обновление, исключение из поиска и удаление проиндексированных материалов.
- Повтор обработки не создаёт дубликаты. Ошибки видны и допускают контролируемый повтор.

### Обязательные границы

- Права и область поиска определяет доверенный серверный код, а не переданный клиентом `projectId`, фильтр или ID кейса.
- Учесть не только изоляцию проекта и среды, но и права пользователя внутри приложения. Flare не должен сам знать, что такое юридический кейс.
- Не возвращать текст, фрагменты или ссылки на материал без права доступа. Не выдавать прямые публичные ссылки на приватные оригиналы.
- После получения кандидатов **обязательно** проверить действующее включение в поиск, наличие готового оригинала и актуальные права пользователя через данные приложения; затем формировать внешний результат. Отсутствие проверки доступа — отказ, а не выдача всех результатов. Даже filename/snippet/score не выдавать для отвергнутых кандидатов. Число результатов может быть меньше запрошенного; не добирать бесконечными запросами.
- Хранение файла и индексация не атомарны. Минимальные служебные checkpoints/desired state допустимы в существующем supervisor, не в новой БД. Использовать его Lifecycle/recovery; application jobs остаются заданиями приложения. Очередь имеет at-least-once доставку: receipt не доказывает exactly-once внешнего эффекта. Повторы сверяют актуальное состояние, чтобы старое задание не вернуло исключённый файл.
- Исключение/удаление сначала закрывает локальную выдачу, затем долговечно удаляет производную копию и chunks у провайдера. Ошибка провайдера оставляет повторяемую уборку, не «успешное удаление». Удаление проекта, отключение/смена binding и restore также должны учитывать эту уборку: не терять её checkpoints и не удалять чужой/operator-owned instance.
- Backup не копирует embeddings. Restore не наследует доступ к исходному индексу или app sessions; повторное включение/индексация в целевой среде явные. Не добавлять автоматические бэкапы или постоянную переиндексацию.
- Поисковый индекс — производные данные, а не единственное хранилище документов или подтверждённых фактов.

Первая проверяемая пара форматов — TXT/PDF в пределах существующих 10 MiB, с учётом более строгих лимитов провайдера. Наличие изображения или `application/octet-stream` в Files не обещает его поисковую обработку. Сохранять корректный тип/расширение при отправке. Другие форматы включать только после проверки встроенной поддержки; не собирать собственный OCR, нарезку текста, embeddings и Vectorize-пайплайн.

По умолчанию возвращать найденные материалы **без дополнительной генерации ответа**: ответ формирует подключённый агент.

## 5. MCP для функций приложения

MCP должен быть тонким слоем над существующими функциями Flare, а не вторым бэкендом.

Базовый вариант — stateless Streamable HTTP в существующем Runtime, через [нативный обработчик транспорта](https://developers.cloudflare.com/agents/model-context-protocol/protocol/transport/) (`agents/mcp/server` уже есть в установленном пакете). Не добавлять McpAgent, новый Durable Object, Worker или собственный JSON-RPC parser по умолчанию. Проверить реальный размер затронутого bundle и совместимость используемого MCP SDK; не обновлять все зависимости ради примера из документации.

### Минимальные возможности

- Явное включение выбранной функции как инструмента в её серверном определении и release manifest. Панель отображает этот контракт, а не хранит второй список инструментов. Старый manifest без MCP-метаданных публикует ноль tools; validateRelease проверяет метаданные и запрет `internal`. Совместимость SDK/runtime проверить при последовательном обновлении, а не молча менять ABI.
- Понятные описания инструментов; схемы аргументов переиспользуются из существующего контракта.
- MCP-имя задаётся явно и уникально в manifest; не заменять `/` в function path на `_` с возможными коллизиями. Опубликованный input должен соответствовать object-схеме аргументов MCP: несовместимый контракт отклонять при сборке, не обходить validator и не добавлять неявную обёртку аргументов.
- Выполнение через штатный admission/call Flare: валидация, авторизация, бизнес-логика и сохранение результата. Проверку opt-in привязать к тому же release, который исполняется, без гонки с deploy. Не использовать привилегированный `AppCapability.runMutation(..., internal: true)` как вход для внешнего агента.
- Изоляция проекта и среды, проверка прав при каждом вызове.
- Возможность отозвать доступ; предсказуемые ошибки для агента.
- Ограниченный ответ без лишней выдачи данных и секретов.

### Безопасность

- Не использовать административные, deploy- или Cloudflare account-токены как пользовательский доступ агента.
- Не превращать функции `internal` в публичные MCP-инструменты.
- Первый поддерживаемый вариант — клиент с явным `Authorization: Bearer` и отдельной действующей app session существующего пользователя. Проверять session в целевой среде на каждом запросе, включая список tools; logout/disable/expiry должны отзывать доступ. Не хранить session в URL, manifest или настройках панели. Это не новый agent principal и не гранулярная делегация прав: агент имеет права пользователя в пределах опубликованных функций, срок и существующие ограничения sessions сохраняются.
- Зафиксировать и проверить один реальный клиент с custom headers (допустим официальный MCP SDK client). Не обещать OAuth discovery, автоматическое продление, browser connectors или произвольные OIDC/dev tokens. Если целевому клиенту нужен OAuth, это отдельное решение с готовым IdP и проверкой audience, а не самописный OAuth-сервер или подмена app identity административным токеном.
- Защищать сам endpoint, а не только ссылку на него в панели.
- Не повторять автоматически mutation с неизвестным результатом. Для повторяемых записей нужен явный механизм идемпотентности.
- Найденные документы и ответы инструментов — данные, не доверенные инструкции и не основание повышать права.

## 6. SDK и панель

### SDK

- Добавлять только API, необходимые для реально работающего поиска и публикации инструментов.
- Конкретные имена API выбрать после анализа существующих соглашений. Не создавать универсальный AI-фреймворк.
- Серверные credentials и возможности не должны попадать в browser bundle.
- Панель, MCP и SDK используют одну реализацию операций и проверок доступа.
- Обновить штатную конфигурацию/установку платформы там, где нужны bindings или ресурсы. Не оставлять работоспособность зависимой от скрытой ручной правки production.

### Вкладка AI

Использовать существующий UI и переключение проекта/среды. Первая версия содержит:

1. **Search** — подключение поискового ресурса, состояние обработки, проверка поиска.
2. **MCP** — адрес подключения, доступные инструменты, состояние настройки доступа.

«Подключение» в первой версии — показ managed configuration и инструкции к operator config, не ещё один provisioning/control plane. Панель не создаёт платные ресурсы и не расширяет grants. Проверка поиска выполняется через разрешённую app action с реальной app-user identity; если такого входа ещё нет, показывать это ограничение, а не выдавать результаты с owner/dev impersonation. Проверка соединения с ресурсом без документов — отдельная административная операция.

Файлы остаются в Files, функции — в Functions, логи — в Logs. Не дублировать эти разделы. Пустые и неподключённые состояния должны быть честными: без демонстрационных данных и декоративных переключателей, за которыми нет реализации.

Не создавать фоновые опросы и отдельную систему телеметрии, если достаточно существующих механизмов. Не показывать выдуманные расходы или токены. Содержимое документов, запросов и секретов не логировать по умолчанию.

## 7. Что не входит в первую версию

- Сущности кейсов, юридические стадии, учебные планы и другие правила будущего приложения.
- Клон Mem0, автоматическое запоминание всех разговоров и разрешение всех противоречий моделью.
- Собственный агентный runtime, автономные циклы и AI-чат.
- Каталог провайдеров и универсальные обёртки над всеми AI API.
- Потоковая генерация ответов и глобальное снятие ограничений outbound.
- Отдельная графовая база или вторая база пользовательских данных в D1.
- Обязательная зависимость от Agent Memory/private beta.
- Одновременное подключение AI Search и собственного поискового пайплайна.
- Собственный аналог AI Gateway или MCP Portal.
- Рефакторинг, обновление всех зависимостей и исправление несвязанных проблем.

Прямые вызовы моделей из приложения рассмотреть отдельным этапом, когда появится конкретный сценарий. Если для согласованного объёма действительно нужна дополнительная возможность, объясни зависимость и выбери минимальное решение, а не расширяй продукт молча.

## 8. Порядок выполнения и проверка

1. Короткий анализ текущего кода и официальной документации, выбор интеграции и модели доступа.
2. Серверная интеграция поиска и SDK, включая состояние обработки и изоляцию.
3. MCP над выбранными функциями с реальной авторизацией.
4. Вкладка AI в существующей панели.
5. Сквозная проверка, узкие регрессионные тесты и обновление необходимой документации.

Не создавать постоянное клиентское приложение внутри репозитория платформы. Для проверки использовать существующие тестовые подходы и небольшой fixture либо временное внешнее приложение.

### Приёмочный сценарий

```text
Приложение загружает документ
→ явно отправляет его в индекс
→ получает правдивый статус готовности
→ агент через MCP ищет и читает разрешённый фрагмент
→ агент вызывает разрешённую mutation приложения
→ результат сохраняется
→ клиент видит изменение через существующую подписку.
```

### Обязательные отрицательные проверки

- Другой пользователь, проект или среда не получает чужие данные.
- Подмена ID и поискового фильтра не обходит права.
- Неопубликованная/internal функция недоступна через MCP.
- Отозванный доступ и удалённый материал не раскрываются через устаревший индекс.
- Повтор фонового задания не создаёт дубликаты.
- Ошибка сервиса или неподдерживаемый файл не показываются как успешная обработка.
- Неопределённый результат записи не вызывает слепой повтор с побочным эффектом.
- Отзыв session действует и на tools/list, и на tools/call; токены панели/CLI/dev не дают MCP-доступ.
- Deploy между выбором инструмента и вызовом не обходит opt-in; внешний MCP-вызов проходит admission без `internal: true` (обычные внутренние вызовы самой action сохраняют свои правила).
- Исключение/удаление во время индексации или поиска, сбой после внешнего upload и повтор старого задания не возвращают скрытый материал.
- Смена/отключение search grant и удаление среды не оставляют потерянную уборку производных копий; restore не обращается к индексу исходной среды.

Начинать с узких тестов затронутого кода; расширять проверки по обнаруженному риску. Для авторизации и изоляции нужны отдельные содержательные проверки. Моки полезны, но не доказывают работу облачной интеграции.

Если нет доступа для реальной проверки Cloudflare или MCP-клиента, завершить доступные локальные проверки и явно указать, что именно осталось непроверенным. Не объявлять сквозной сценарий работающим только по сборке.

## 9. Ограничения выполнения

- Сохранять чужие изменения. На момент составления задания в `docs/production-runbook.md` уже были незакоммиченные изменения; перед работой заново проверить состояние Git.
- Не читать и не выводить секреты без необходимости, не переносить credentials в код, документацию или браузер.
- Не выполнять деплой, публикацию пакета, создание платных облачных ресурсов, удаление данных и изменение действующих политик доступа без отдельного согласования.
- Рискованные изменения хранения/конфигурации делать с понятным путём отката и без сброса существующих проектов.
- Не создавать отчётную инфраструктуру, копии проекта и длинные промежуточные документы. Достаточно краткого решения по архитектуре, рабочих изменений и итогов проверки.

## 10. Что сообщить в конце

Кратко перечислить:

1. Что переиспользовано, что добавлено и какие пункты плана скорректированы после анализа.
2. Как приложению использовать новые возможности SDK и подключить агента.
3. Какие проверки реально выполнены и каков результат.
4. Какие настройки, разрешения, облачные действия или ограничения остались.

Не утверждать, что Flare поддерживает «все AI-возможности». Цель — один небольшой, безопасный и полностью связанный набор возможностей для будущего приложения.
