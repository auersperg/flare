# Единое ядро памяти, кейсов и профилей агентов

Дата: 2026-11-03. Статус: проект архитектуры для согласования, не реализованная функциональность.

## 1. Что строим

Одно принадлежащее пользователю онлайн-хранилище знаний и состояния работы. Разные агенты получают из него общую память, выбранный кейс, документы и профиль поведения; после работы сохраняют проверяемый результат и точку продолжения.

Пользователь подтвердил: **всем его авторизованным агентам доступны все его кейсы**. Это не публичный доступ. Сохраняются изоляция владельцев, разрешения чтения/записи и отзыв отдельного OAuth-подключения. Кейсы и теги в первой версии организуют контекст, а не создают дополнительные границы доступа между агентами владельца.

Примеры школьного, медицинского дела и спора с компанией — сценарии проектирования, а не уже существующие пользовательские дела. Не создавать их автоматически и не записывать примеры как личные факты.

Единое ядро не означает единую модель или постоянно работающего агента. MCP — интерфейс к состоянию, а не ещё один посредник, который сам рассуждает за вызывающую модель.

## 2. Выбранный подход и альтернативы

Уточнённое направление пользователя: **Memory — самостоятельный проект на Flare, а Flare — его универсальный бэкенд и платформа**. У Memory свои репозиторий, схема данных, интерфейс, версии и деплой. Существующий модуль памяти Auer — исходная реализация для переноса, а не постоянное место нового продукта. SQLite хранит канонические данные, Files — оригиналы документов, AI Search — производный индекс, существующие jobs — обработку. MCP, SDK и собственный Codex runner используют одни прикладные операции Memory.

Рассмотренные альтернативы:

| Подход                              | Польза                                                        | Почему не выбран                                                                                   |
| ----------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Перенести Mem0 или Graphiti целиком | Готовые механизмы извлечения/поиска                           | Другой стек и зависимости; кейсы, профили, права и передачу работы всё равно строить отдельно      |
| Подключить внешний сервис памяти    | Быстрее получить готовую память                               | Ещё один источник состояния, отдельная обработка чувствительных документов, синхронизация удаления |
| Отдельный Memory на Flare           | Переиспользование платформы при независимом развитии продукта | Выбрано; недостающие универсальные возможности добавляются во Flare, а не обходятся внутри Memory  |

Не переносить прикладные медицинские/школьные/юридические модели в универсальный runtime Flare. Auer становится одним из клиентов Memory. Не поддерживать два независимых источника памяти после переключения; до проверенного переноса старый путь остаётся рабочим.

### Достаточность платформы Flare

Требование пользователя: **функционала Flare должно хватать для реализации Memory через штатный SDK, CLI и runtime, без собственной параллельной инфраструктуры**. Это требование к результату, не утверждение, что всё уже реализовано и проверено.

В платформе должны быть достаточные универсальные механизмы:

- схема данных, индексы, пагинация и атомарные mutations для согласованного состояния;
- авторизация пользователей и подключений, отзыв доступа и проверка прав;
- хранение/выдача файлов и пригодные контракты поисковой обработки документов;
- поиск записей и файлов с metadata, проверкой доступа и жизненным циклом индекса;
- надёжные фоновые задачи, повторы и защита от выполнения устаревшей работы;
- MCP-публикация прикладных функций и типизированный SDK без дополнительного прокси;
- существующий запуск Codex и доставка его событий, без нового агентного движка;
- создание отдельного приложения, миграции, конфигурация, деплой и наблюдаемость через штатный путь.

Перед реализацией проверяем сквозные сценарии Memory против публичных контрактов Flare: что уже есть, что действительно не хватает и где проходит граница. Наличие примитива ещё не подтверждает достаточность его лимитов или поведения. Конкретный общий пробел исправляем минимальным изменением в Flare с узкой проверкой; не добавляем возможности «на всякий случай». Memory не обращается к внутренним файлам платформы и не дублирует её auth, storage, search или jobs. Его кейсы, профили, связи, checkpoint и правила качества остаются прикладными функциями на SDK.

## 5. Предметная модель

Один владелец, единый набор данных; разделение общей и кейсовой памяти — явное.

| Объект                      | Содержание и роль                                                                                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Case**                    | Постоянный ID, заголовок, цель, теги, статус, текущая стадия, версия, открытые вопросы и следующие шаги                                                                |
| **Entity**                  | Человек, организация, проект или другой участник. Устойчивый ID, названия/алиасы; связи с кейсами. Не путать человека с агентом                                        |
| **Fact**                    | Атомарное утверждение, `scope = global` или конкретный кейс, связанные сущности, источник, версия и актуальность                                                       |
| **Relation**                | Типизированная связь между сущностями/фактами/доказательствами с проверяемыми концами и происхождением                                                                 |
| **Document**                | Ссылка на оригинал Flare Files, версия, название, источник, связи с кейсами, состояние обработки. Не ещё одна копия бинарного файла                                    |
| **Case event / checkpoint** | Единая типизированная лента: фактическое событие, решение, изменение состояния или точка передачи работы. Не две параллельные истории                                  |
| **Agent profile**           | Пользовательская конфигурация: роль, стиль, специализация, рабочие правила, шаблон результата, версия. Не секреты, не полномочия и не сертификат компетентности модели |

Это логические сущности, не требование создавать семь микросервисов или семь обязательных новых таблиц. Конкретную нормализацию выбрать при реализации с учётом существующего SDK; не строить универсальный schema engine.

### Общая память и кейсовая память

- Общая: стабильные предпочтения и факты, действительно полезные вне одного дела.
- Кейсовая: обстоятельства, документы, утверждения сторон, решения и события конкретного дела.
- Теги — удобные метки поиска, не замена постоянному `caseId`.
- Перенос чувствительного факта из дела в общую память не делать автоматически только потому, что он часто встречается.
- Факт имеет одно каноническое место; связь нескольких кейсов не требует копировать факт. Источник/документ может быть связан с несколькими делами.
- По умолчанию запрос по выбранному делу использует его контекст и релевантную общую память. Поиск по всем делам доступен явно; общие права не означают выдачу всего архива в каждый запрос.

### Профиль агента: переносимая «душа»

Храним пользовательские настройки поведения, а не имитацию отдельной личности или собственную модель. Профиль «юрист», например, может требовать различать утверждения сторон и доказательства, фиксировать юрисдикцию, проверять источники и не выдавать черновик за отправленное письмо.

Редактирование/публикация профилей — отдельная owner-операция через интерфейс. Обычные `memory_save`, документы и запросы внешних агентов не меняют настройки профиля. Профиль не может повысить OAuth-права, обойти правила клиента или открыть чужие данные.

Выбранная модель и её возможности принадлежат исполняющему клиенту. MCP может вернуть требуемую специализацию и инструкции, но не гарантирует одинаковое поведение ChatGPT, Gemini, Codex и других моделей. В собственном runner профиль применяется явно; внешнему клиенту нужен поддерживаемый skill/инструкция/нативный hook.

## 6. Связи и качество знаний

Минимальный набор:

1. **Сущностная связь:** «Анна — представитель — школы», «документ — относится к — кейсу».
2. **Изменение:** новая версия факта заменяет старую; использовать существующий механизм версий, не хранить ещё один конкурирующий `supersedes`-граф без необходимости.
3. **Дополнение:** новый факт уточняет другой, не отменяя его.
4. **Доказательство:** утверждение ссылается на версию документа/сообщения и страницу либо доступный фрагмент.
5. **Вывод:** отдельный тип, с зависимостями от точных версий оснований. В первой версии предпочтительно вычислять при ответе, а не постоянно плодить производные факты.

Семантическое сходство помогает искать кандидатов, но не является доказательством связи. Не объединять людей по одному имени. При неоднозначности сохранять разные сущности до уточнения.

Различать `user_statement`, `document_statement`, `agent_report`, `inference`, а также подтверждённый результат внешней операции. «Пользователь сообщил диагноз» не равно «диагноз независимо подтверждён». «Агент составил письмо» не равно «письмо отправлено».

**Правило происхождения:** сервер сам присваивает владельца, подключение, время записи и тип канала. Внешний агент не может переданным полем объявить свой текст проверенным результатом инструмента. Его цитата/копия результата сохраняется как предоставленное им свидетельство; ссылка на чужой чат сама по себе не подтверждает содержимое. Подтверждённое внешнее действие требует результата собственной проверенной интеграции или явного подтверждения владельца; эти основания различаются. Даже подлинный документ может содержать ошибочное утверждение.

**Правило конфликтов:** автоматическое извлечение не отменяет конкурирующее доказательство молча. Явное исправление владельца может сменить актуальную версию с сохранением истории; новая редакция источника обновляет утверждения этого источника, но не автоматически все сведения по теме. При несовместимых источниках храним конфликт и показываем обе позиции с датами. Внешний агент может предложить исправление, но не повысить свой `agent_report` до подтверждённого факта. Исторические MCP-записи сохраняют прежнее происхождение, без задним числом выданного статуса подтверждения.

Учитывать две временные оси: когда событие произошло/утверждение действовало и когда запись поступила в систему. Неизвестное время оставлять неизвестным. Старая справка, загруженная позже нового решения, не отменяет новое решение автоматически.

Исправление основания делает зависимый вывод устаревшим; удаление основания исключает зависимый контекст из выдачи до пересчёта. Не выводить искусственные числовые оценки достоверности без калибровки.

## 7. Реальное продолжение дела другим агентом

Ключевой объект — **checkpoint**, а не длинное резюме всего чата:

- цель и стадия дела;
- что действительно сделано, с источниками/результатами;
- решения и причины;
- открытые вопросы, блокеры и незавершённые действия;
- следующий рекомендуемый шаг;
- ссылки на документы и версии фактов;
- автор записи, OAuth-подключение, время, версия кейса;
- профиль и версия профиля, использованные агентом.

Поток работы:

1. Агент выбирает явные `caseId` и `profileId`; получает небольшой пакет актуального контекста.
2. По необходимости дочитывает документы и историю через адресные запросы.
3. Выполняет работу в своём клиенте/рантайме.
4. Сохраняет факты, события и checkpoint с ожидаемой версией и ключом идемпотентности.
5. Другой агент открывает тот же кейс и начинает с принятого состояния, а не из пересказа пользователя.

Пакет возвращает: профиль отдельно от недоверенных данных; краткое состояние кейса; релевантную общую/кейсовую память; последние существенные события; checkpoint; ссылки на источники; известные пробелы/конфликты; версию снимка и признак усечения.

Для первой версии целевой верхний бюджет всего текстового пакета — **8 КиБ**, включая профиль и ссылки, а не 8 КиБ на каждый раздел. Полные документы и старая история дочитываются отдельно. Распределение бюджета и приоритеты проверяются на реальных кейсах; размер не является гарантией качества.

Если snapshot успел устареть, запись не должна затереть работу другого агента. Изменение состояния, событие и checkpoint фиксируются атомарно в одной mutation; клиент получает ID и принятую версию. Повтор после сетевого сбоя с тем же ключом не создаёт дубликат. Подтверждение показывает именно успешную серверную запись.

Не переносим скрытые рассуждения модели, незавершённые процессы, cookie, подписку, ключи или runtime другого клиента. Передаётся явное рабочее состояние. Чужой авторизованный агент может продолжить дело только если умеет читать/записывать этот контракт.

## 8. Документы и обработка

Оригинал загружается один раз через Flare Files. Прикладная запись связывает его с кейсом. При новой редакции сохраняется новая версия источника, а не незаметная замена доказательства под прежней ссылкой.

Обработка: загрузка → извлечение текста → индексация/извлечение утверждений → доступность. Состояния видны пользователю; ошибка или ожидание индексации не выглядят как готовый результат.

Не считать OCR поддержанным без проверки существующего пути: скан без текста должен честно отображаться как требующий распознавания, а не порождать выдуманные факты. Точный перечень PDF/Office/изображений, лимиты и доступность страниц проверить отдельным небольшим тестом до обещания поддержки.

Поиск оригиналов и выдача ссылки на скачивание проверяют владельца. URL не превращается в бессрочный публичный доступ. Удаление связи документа с одним кейсом отличается от удаления оригинала, используемого ещё в другом деле; UI должен показывать эту разницу.

Автоматическое извлечение не вызывает отдельный Codex для каждого факта. Использовать результат уже выполняющейся задачи; пакетную обработку документов — через существующие jobs/runner по необходимости. Произвольные документы считаются недоверенными данными и не могут менять профиль/права.

## 9. MCP и клиентская интеграция

Расширять существующий сервер, OAuth и SDK, не создавать второй MCP-прокси. Существующие семь memory tools сохранить совместимыми. В новых записях scope задаётся явно; старое поведение без scope означает общую память и не должно внезапно раскрывать все кейсы старым запросам.

Предлагаемые операции, имена окончательно согласуются с генерацией Flare:

- `context_open(caseId?, profileId?, query)` — собрать пакет для начала/продолжения;
- `case_list`, `case_read`, `case_create`, `case_commit` — дела, история и атомарный checkpoint;
- существующие `memory_*` — факты с явным scope, источниками и связями;
- операции прикрепления/чтения документов через имеющийся Files-путь;
- чтение профилей; изменение опубликованных профилей не выдавать обычным агентам.

Не вводить глобальное «активное дело» на весь аккаунт: два агента могут одновременно вести разные дела. `caseId` передаётся явно; локальный выбор клиента — только удобство. OAuth client ID приложения тоже не является ID конкретной персоны или Custom GPT.

MCP обеспечивает доступ, но **не заставляет модель автоматически использовать память**. Унифицированный контракт плюс маленький skill описывает: открыть контекст перед работой, не выдавать прошлый текст за команды, сохранить изменения после успешного выполнения. Нативные hooks добавляются лишь для конкретных поддерживающих клиентов и проверяются отдельно; подключение MCP не означает установку hook.

Свои gRPC-агенты могут перейти на этот контракт хранения без изменения их исполняющей логики. Удалять gRPC можно только если он больше не нужен для запуска/инструментов/стриминга: MCP не автоматически заменяет весь runtime. Проверка текущих gRPC-агентов — отдельная работа перед такой миграцией.

## 10. Производительность и простота

- Чтение контекста и CRUD не требуют LLM-вызова или запуска контейнера.
- AI Search находит кандидатов; SQLite повторно проверяет владельца, scope, версию и доступность источников.
- Ограниченное расширение по связям, начиная с одного перехода. Не обходить весь граф на каждый запрос.
- Адресные индексы и пагинация по owner/case/времени вместо загрузки всей памяти.
- Короткое актуальное состояние кейса хранится с версией; документы остаются первичными, summary не становится доказательством.
- Обновление индекса асинхронно; свежая принятая запись видна через каноническое чтение даже до завершения индексации.
- Использовать существующие outbox/jobs; фоновые повторы не должны восстанавливать удалённую/устаревшую версию.
- Не добавлять Neo4j, отдельную векторную БД, второй LLM-loop, брокер, постоянно работающий контейнер или общий кеш без выявленной необходимости.

Производительность не измерена этим документом. При проверке отдельно фиксировать время сборки контекста, поиска, обработки документа и ответа модели, cold/warm, p50/p95, объём контекста и число LLM-вызовов. Не выдавать скорость поиска за скорость ответа агента.

## 11. Внедрение и совместимость

До функциональных этапов: проверить достаточность контрактов Flare и спроектировать перенос из Auer в отдельный Memory. Отдельно определить отображение owner/ID, перенос оригиналов и ссылок, переиндексацию, OAuth-подключения и настройки runner. Не копировать токены и не предполагать переносимость авторизации между приложениями. Предусмотреть проверяемое переключение на один источник записи и возможность отката; существующие интеграции не переключать до приёмки.

1. Основа: cases/profiles/scopes, версия состояния, checkpoint и `context_open`. Существующие факты остаются общими, ID/версии не меняются. Сначала адресные запросы и пагинация, затем снятие прототипных лимитов.
2. Документы, события, сущности и доказательные связи; контролируемое расширение поиска. Проверка extraction/OCR на поддерживаемых форматах.
3. Переносимый skill и собственный runner; затем один независимый внешний клиент. Остальные клиенты — по проверенной совместимости, а не обещанию «любой агент».
4. Простой интерфейс: список дел, текущее состояние, документы, таймлайн, профиль, checkpoint, видимый результат сохранения. Графическая карта связей — необязательная визуализация, не условие работоспособности.

Это порядок развития, не детальный план кодовых изменений. Перед внедрением: согласовать дизайн, составить узкий план миграции и проверить staging. Миграции сначала добавочные; обратимость старого пути сохраняется до приёмки. Не менять старую семантику удаления и OAuth автоматически.

Скрытие из поиска, архивирование кейса и окончательное удаление — разные операции. При окончательном удалении убрать содержимое, истории, зависимый контекст и индекс согласно выбранной политике; минимальный tombstone без содержимого может блокировать восстановление старым job. Для разделяемого источника нельзя удалить оригинал вместе с одним кейсом незаметно для других. Политику резервных копий и срок окончательного удаления проверить/показать отдельно, не обещать мгновенное исчезновение всех копий.

**Забывание при сохранённом оригинале:** принятый принцип — не восстанавливать забытое при следующей обработке того же источника. Для первой версии связанные версии источников исключаются из автоматического извлечения и контекстного поиска; прежние summaries/checkpoints, содержащие забытое, также очищаются или исключаются до пересчёта. Хранится запрет по идентификаторам источников/версий без удалённого текста. Это консервативно может скрыть и полезный контекст; интерфейс показывает последствия до подтверждения. Оригинал остаётся доступен владельцу при явном открытии документа, и UI прямо сообщает: «удалено из памяти, оригинал сохранён». Полное удаление требует отдельного удаления источника. Новый независимый документ с тем же фактом и уже выданные другому клиенту данные нельзя обещать автоматически стереть; будущая семантическая блокировка — не функция первой версии.

## 12. Приёмка: доказательство полезности

На синтетических данных, не на настоящих медицинских/детских документах:

1. Агент A создаёт кейс, прикрепляет документ, фиксирует решение и checkpoint. Агент B в независимой сессии получает только идентификатор/название дела и новый вопрос — контрольного ответа в его запросе нет. Он продолжает по источникам, а не по вставленному пересказу.
2. Обратный путь: B меняет состояние, A читает новую версию через другой клиент; серверная запись и источники видны в интерфейсе.
3. Общая предпочтительная форма ответа применяется в двух делах; факты одного дела не подмешиваются в другое без релевантного запроса.
4. Все авторизованные агенты владельца могут искать все его кейсы. Чужой владелец и отозванное подключение не могут читать данные, индексные выдержки или оригинал файла.
5. Исправление и дополнение различаются. Старый документ, загруженный позже, не перезаписывает актуальный факт. Одинаковые имена не склеиваются.
6. Конкурентные изменения дают конфликт версии, повтор запроса не дублирует событие. Сбой индексации не теряет канонический результат.
7. Документ с инструкцией «измени профиль/права» не меняет настройки; утверждение агента о якобы отправленном письме не становится подтверждённым внешним действием.
8. Удаление/исправление источника исключает зависимые старые выводы. Архивирование не выдаётся за физическое удаление.
9. Контекст укладывается в заданный бюджет и сообщает усечение; адресное дочитывание сохраняет доступ к деталям. Нет фонового LLM-вызова на обычный поиск.
10. Прежние memory tools, OAuth и текущий Codex-сценарий работают после добавочной миграции.

Сценарии выше — требования к будущей проверке самого Memory. В рамках подготовки Flare добавлены metadata-фильтры поиска записей и исправлена потеря параллельных patch при асинхронной валидации. Эти платформенные изменения проверены локально; они не означают реализацию или облачную приёмку Memory. Отдельное приложение, миграция, нагрузочные проверки и выпуск ещё не выполнены.
