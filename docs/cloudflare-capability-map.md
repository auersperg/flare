# Cloudflare: карта возможностей и потребления ресурсов

**Срез: 11 октября 2026 года.** Для выбора архитектуры Flare, а не для включения всех сервисов аккаунта. Связанная [карта реализации Flare](flare-architecture-map.md).

## Как читать карту

- Проверены официальный [каталог Cloudflare](https://developers.cloudflare.com/directory/) и overview каждого из **138 разделов**. В конце — полный реестр этого среза. Раздел документации, umbrella-платформа и отдельный платный продукт — не одно и то же.
- Подробно разобраны вычисления, данные, доставка, безопасность, наблюдаемость и инструменты разработки. Также перечислены важные API внутри Workers, которых нет отдельными карточками каталога.
- **GA** означает подтверждённую общедоступность указанного компонента, **beta** — явно объявленный экспериментальный статус. Отсутствие beta-надписи не доказывает GA. Статус неизвестной функции обозначается «не подтверждён».
- Дата запуска/GA взята из release notes. **Дата обновления документации в реестре не является датой запуска**, версией сервиса или доказательством его новизны. Cloudflare — постоянно обновляемая платформа, не единый пакет с номером версии.
- Доступность зависит от аккаунта, региона, плана и конкретной функции. Проверка документации не означает проверку entitlement в вашем аккаунте. Тарифы USD, без налогов; включённые объёмы и округление смотреть в первоисточнике.
- «Лучший» ниже означает **подходящий нашей нагрузке и требованиям**, а не универсально самый быстрый, новый или дешёвый. Результаты нагрузки и актуальный счёт этот документ не подменяет.

## 1. Главное правило: развёрнут ≠ постоянно работает

| Состояние                                                       | Что оплачивается / расходует лимит                                                                              |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Worker опубликован, событий нет                                 | Нет постоянно арендованной VM. Подписка и отдельное хранение могут оставаться                                   |
| HTTP / RPC / queue / cron событие                               | Вызовы и CPU соответствующих сервисов; один пользовательский вызов может проходить несколько биллинговых границ |
| Durable Object без работы, допускающий hibernation              | Нет duration; SQLite остаётся долговечным                                                                       |
| WebSocket открыт через Hibernation API, обработчики завершились | Соединение может сохраняться без постоянно активного JS. Следующее событие пробуждает объект                    |
| DO не может hibernate                                           | Duration продолжается, даже если приложение выглядит «ничего не делает»                                         |
| Будущий alarm                                                   | Не JS-таймер, удерживающий процесс. Запись расписания и будущее пробуждение имеют стоимость                     |
| Данные лежат в R2 / SQLite / KV                                 | Хранение остаётся; отсутствие пользователей не удаляет его и не отменяет overage                                |
| Регулярный cron / health check / индексация                     | Работа идёт и без посещений. Это явно заказанная фоновая нагрузка                                               |
| Живой Container / headless browser                              | Иная модель ресурсов; нельзя автоматически переносить экономику Workers                                         |

У DO hibernation блокируют постоянные JS-таймеры, незавершённые обработчики/I/O, исходящие WebSockets и обычный серверный WebSocket через `accept()`. Сохранять нужное состояние в storage/attachments, а не рассчитывать на heap. Пауза до физической hibernation сама по себе не означает платный простой: idle-объект, уже подходящий для неё, не тарифицируется по duration. [Lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), [WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

**Правило Flare:** доступность 24/7 нужна; активное выполнение 24/7 — нет. Не добавлять keep-warm, polling и служебные heartbeats ради самой доступности.

## 3. Вычисления и frontend

Стабильные идентификаторы CF-* используются в [карте Flare](flare-architecture-map.md).

### CF-WORKERS

**Workers:** HTTP/event compute, JS/TS, Web APIs, поддерживаемые языковые/runtime-интеграции. Нет своей постоянно поднятой VM. Вызовы и CPU по Workers Standard; ожидание I/O не равно active CPU. Предпочтительно для двух shared Worker Flare. Bun — локальная сборка/CLI, **не облачный runtime**. [Workers](https://developers.cloudflare.com/workers/), [CPU](https://developers.cloudflare.com/workers/platform/limits/).

### CF-DYNAMIC

**Dynamic Workers / Loader:** код загружается по требованию без обычного deploy Worker на каждый проект. Open beta; Workers Paid. `.get(stableId, ...)` — правильная основа; случайные IDs или `.load()` на каждый вызов умножают creations. Цена включает startup CPU, не только работу handler. [Loader](https://developers.cloudflare.com/dynamic-workers/), [API](https://developers.cloudflare.com/dynamic-workers/api-reference/).

### CF-FACETS

**Durable Object Facets:** динамический DO как дочерняя изолированная единица с собственным storage. Родитель владеет физическими WebSockets/alarms. Постоянное имя facet сохраняет данные между версиями; `abort()` перезапускает, `delete()` уничтожает. Facets относятся к beta Dynamic Workers, не наследуют автоматически все гарантии/лимиты обычных DO. Подходят Flare лучше, чем Worker на каждый проект или общая app-таблица D1. [Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/).

### CF-ASSETS

**Workers Static Assets:** HTML/JS/CSS на edge; без запуска Worker asset-запросы бесплатны и не ограничены по количеству. `run_worker_first` вызывает script и меняет экономику. Для статического Astro dashboard не нужен SSR/container. [Assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/).

### CF-RPC

**Service bindings / Workers RPC:** внутренние capability-вызовы, без публичного account API token. Ordinary Worker service binding не добавляет отдельную Worker request charge, CPU работы учитывается. **DO sessions и Dynamic Worker RPC имеют собственные правила** — нельзя объявлять весь RPC бесплатным. [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/), [RPC](https://developers.cloudflare.com/workers/runtime-apis/rpc/).

### CF-EGRESS

**Dynamic bindings / outbound gateway / resource limits:** приложениям выдаются scoped capabilities; роли данных без internet egress. Actions могут иметь разрешённый outbound, ограничения CPU/subrequests. Это нативные изоляционные границы, не собственный proxy mesh. [Bindings](https://developers.cloudflare.com/dynamic-workers/usage/bindings/), [egress](https://developers.cloudflare.com/dynamic-workers/usage/egress-control/), [limits](https://developers.cloudflare.com/dynamic-workers/usage/limits/).

## 4. Базы данных и хранение: не взаимозаменяемые варианты

### CF-DO

**Durable Objects:** один адресуемый объект — state/coordination; запросы, SQL и alarms. Для supervisor каждой среды это естественная единица изоляции. Один горячий DO не становится горизонтально распределённой БД. [DO](https://developers.cloudflare.com/durable-objects/), [limits](https://developers.cloudflare.com/durable-objects/platform/limits/).

### CF-SQLITE

**DO class lifecycle (обновление 28 сентября 2026):** declarative `exports` заменяет историю imperative `migrations`: live SQLite class, deleted/renamed/transferred states и native reconciliation. Для существующего Worker нельзя смешивать обе формы; удаление namespace необратимо. В Big Bang Flare применён новый `EnvironmentSupervisor`, старый namespace удалён; это не data-preserving rename. [Официальная модель exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/).

**SQLite-backed DO:** нативные `storage.sql.exec`, indexes, transactions; рядом с координатором и facet. Для новых классов Cloudflare рекомендует SQLite вместо legacy KV-backed DO. Drizzle не отдельная Cloudflare БД: это optional слой доступа/миграций, его необходимость определяется публичным API. [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), [выбор backend](https://developers.cloudflare.com/durable-objects/reference/legacy-key-value-storage-backend/).

### CF-D1

**D1:** отдельная serverless SQL DB; подходит общему каталогу, аудитам и административным выборкам. Стоимость строк/хранения, а не аренда постоянно активного SQL-сервера. D1 Sessions/read replication — отдельная возможность с consistency/bookmarks; не бесплатное ускорение любой записи и не встроенный live engine. [D1](https://developers.cloudflare.com/d1/), [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/).

### CF-R2

**R2:** binaries/builds/files/exports. Standard storage подходит частым обращениям; Infrequent Access имеет retrieval/minimum storage условия и может быть хуже для маленьких часто читаемых файлов. Не хранить app rows или permissions только в имени публичного blob. [R2](https://developers.cloudflare.com/r2/), [storage classes](https://developers.cloudflare.com/r2/buckets/storage-classes/).

## 5. Live, очереди и расписания

### CF-WS

**WebSocket Hibernation API:** долгоживущее соединение без постоянно работающего JS. Supervisor владеет сокетами; сохраняет attachments/subscriptions и восстанавливает состояние после eviction. Нативный transport не умеет сам понимать изменения результатов SQL queries. [Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

### CF-ALARMS

**DO alarms:** долговечное пробуждение, at-least-once; не бесконечный `setInterval`. Один физический alarm объекта требует выбора ближайшего события. Для многих задач лучше официальный Scheduler, не самодельный timer wheel. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/).

### CF-MODULES

**Модульные Lifecycle / WebSockets / Scheduler из Agents:** библиотечные компоненты Cloudflare поверх DO APIs, не отдельный оплачиваемый сервис. API экспериментальны. Использовать минимальные публичные modules; full Agent/AI/MCP необязателен. Lifecycle объединяет alarm, readiness/recovery; Scheduler обслуживает cron/delays. Это собственный код SDK Cloudflare, не API «встроено в workerd». [Lifecycle](https://github.com/cloudflare/agents/blob/48d9c36f5f1ff18a91fbf0659b9a8e026d1cac43/docs/agents/lifecycle.md), [Agents](https://developers.cloudflare.com/agents/).

### CF-QUEUES

**Queues:** доставка jobs, retries, DLQ, batching; push consumer вызывается событием. Нет Flare-процесса, который непрерывно опрашивает очередь. Гарантия **at-least-once**, не exactly-once внешнего эффекта. Native delay до 24 часов; длительные app schedules требуют отдельного persisted scheduler. [Guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [batching/delay](https://developers.cloudflare.com/queues/configuration/batching-retries/).

### CF-CRON

**Workers Cron Triggers:** расписание deployed Worker, хорошо для общего обслуживания. Не готовый каталог тысяч динамических расписаний каждого project/environment. Каждый scheduled event расходует ресурсы, даже когда посетителей нет. [Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/).

### CF-WORKFLOWS

**Workflows:** многошаговые процессы, durable sleeps/events/retries. Для цепочек подтверждения оплаты/длительных business flows лучше собственной orchestration. Для одношагового job Queues проще. После 10.08.2026 учитываются steps и stored state, помимо Workers CPU/requests. **Dynamic Workflows** теперь имеют отдельный API; возможность существует, в Flare не подключена. [Workflows](https://developers.cloudflare.com/workflows/), [Dynamic Workflows](https://developers.cloudflare.com/dynamic-workers/usage/dynamic-workflows/).

### CF-K2

**K2:** public beta, append-only durable log с replay и независимыми consumers. Подходит event streaming, не drop-in замена retry/DLQ job queue. Pricing от 06.10.2026 говорит, что billing ещё не включён; объявленные будущие meters — produce/consume bytes и retention. Не планировать постоянную бесплатность beta. [K2](https://developers.cloudflare.com/k2/), [pricing](https://developers.cloudflare.com/k2/platform/pricing/).

**Realtime SFU / RealtimeKit / TURN / MoQ** решают audio/video/media delivery, а не reactive SQLite queries. Для обычного dashboard это лишние сервисы. [Realtime](https://developers.cloudflare.com/realtime/).

## 6. Безопасность, домены и конфигурация

### CF-ACCESS

**Cloudflare Access:** edge login/policy для admin dashboard. Не заменяет авторизацию пользователей приложения и owner/editor/viewer внутри Flare. Access application должна защищать все доступные dashboard hostnames. У Static Assets router есть ограничение `ctx.access`; проверка подписанного assertion — оправданный fallback, не повод снимать защиту. [Access](https://developers.cloudflare.com/cloudflare-one/access-controls/), [Workers Access](https://developers.cloudflare.com/workers/configuration/access/), [router limitation](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/).

### CF-SECRETS

**Worker secrets** для фиксированных core secrets; **Secrets Store** для управляемого account-level reuse (open beta). Это разные варианты. App получает только разрешённый secret своего окружения, не общий binding/API token. Secret read/write и изменение binding конфигурации не считать бесплатным универсальным динамическим namespace. [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/), [Secrets Store binding](https://developers.cloudflare.com/secrets-store/integrations/workers/).

### CF-RATELIMIT

**Rate Limiting binding:** native fast local rate limit в Worker; не строгий глобальный бюджет аккаунта. WAF/rate rules действуют раньше application compute там, где поддерживаются route/plan. CPU limits и подписки не ограничивают все виды billable usage. [Binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [WAF rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/).

### CF-DOMAINS

**DNS / SSL / Custom Domains:** короткие публичные адреса frontend/runtime/dashboard. Хостнеймы не добавляют постоянно активный compute. DNS mapping и Access redirect settings должны меняться согласованно. Cloudflare for SaaS/custom hostnames нужен, когда чужие клиентские домены обслуживает сама платформа, а не при каждом новом внутреннем project. [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/), [Cloudflare for SaaS](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/).

### CF-ANALYTICS

- **GraphQL Analytics:** account/service usage и метрики; schema/dataset availability проверить по аккаунту. Считать daily Dynamic creations аккуратно, не произвольный uniq по всему месяцу. [GraphQL](https://developers.cloudflare.com/analytics/graphql-api/).
- **Analytics SQL binding:** SQL к поддерживаемым account datasets, без отдельного analytics token в Worker. Требуется поддерживаемый Wrangler; API beta. Не поддерживает Log Explorer-backed datasets: нельзя обещать доступ к любому log через него. [SQL binding](https://developers.cloudflare.com/analytics/sql-api/workers-binding/).
- **Workers Analytics Engine:** собственные product-level events/metrics, sampled analytics. Отдельные write/query meters. Pricing от 23.04.2026 сообщает: биллинг пока не включён; опубликованные будущие цены не считать вечным free-tier. [Engine pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/).
- **Notifications / Resource Tagging:** уведомления о лимитах/событиях и атрибуция ресурсов. Resource Tagging public beta; не заменяет собственный accounting нескольких проектов в одном Worker. [Notifications](https://developers.cloudflare.com/notifications/), [Tagging](https://developers.cloudflare.com/resource-tagging/).

### CF-TOOLING

**Wrangler / `cf` beta / Cloudflare Vite plugin / APIs / Terraform / Pulumi:** build/deploy/provisioning. CLI не остаётся облачным daemon после установки. CI/builds расходуются при запусках; ограничить watch paths и duplicate workflows. `cf` — новый универсальный beta CLI, не обязательная срочная замена работающего Wrangler. Core Worker Versions/Previews — нативный release инструментарий платформы; это **не** zone Version Management и не транзакция миграции app facet. [Wrangler](https://developers.cloudflare.com/workers/wrangler/), [`cf`](https://developers.cloudflare.com/cf/), [Builds](https://developers.cloudflare.com/workers/ci-cd/builds/), [Versions](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/).

**Поправка прежних ожиданий:** старый список тарифов в переписке не является актуальным источником. Сейчас DO SQLite указывает 5 GB-month, а SQL writes — $1/M, не $0.001/M. Workers Logs и Workers Logpush — разные тарифы. Включённые pools считаются по правилам продукта/аккаунта, а не умножаются на количество проектов Flare.

С **1 декабря 2026**, согласно уже объявленной модели, shared Observability Paid: 50 GB ingestion и 10 GB-month storage за cycle; сверх — $0.25/GB и $0.10/GB-month. Это **будущий** тариф. Размер log payload станет особенно важен; не логировать целые документы/файлы. Unsampled security datasets имеют отдельные условия. [Объявленная Observability pricing](https://developers.cloudflare.com/observability/pricing/).

Общая модель:

```text
счёт = base subscriptions
     + overage Workers requests/CPU (включая Dynamic execution/startup)
     + daily-unique Dynamic creations
     + DO requests/duration + SQLite rows/storage
     + D1 rows/storage + R2 operations/storage
     + Queue operations + logging/другие явно включённые сервисы
```

Физический размер heap не равен тарифицируемой allocation DO. HTTP latency, CPU ms, duration и GB-s — разные величины. Dashboard счётчик actual WebSocket events может отличаться от billable requests. Facet/RPC accounting проверять cloud usage отдельно; не складывать неизвестные внутренние calls как доказанные независимые тарифные единицы.

Минимальный запрос к этой модели: объём пользовательских операций, уникальные runtime роли/дни/релизы, число live queries, реальные активные секунды DO, SQL rows, file sizes/operations, число cron/jobs/retries и логи. Без этого обещание «$5 хватит на любое количество проектов» неверно.

## 11. Что переоценивать при следующем обновлении

1. Сверить directory и changelog: renamed/new/deprecated продукты; не добавлять новый binding автоматически.
2. Проверить GA/beta именно API, который планируем использовать, а не umbrella-продукта.
3. Перечитать pricing перед включением: особенно beta billing, Observability с декабря, Artifacts с октября.
4. Проверить ограничения/доступность в аккаунте без изменения посторонних ресурсов.
5. Для каждого решения заполнить связь с CF-ID, workload, idle-модель, migration cost и cloud acceptance.
6. Не мигрировать ради номера версии: измерить latency/CPU/storage/стоимость на сопоставимом тесте.

**Итог выбора:** Workers + Dynamic Loader/Facets + SQLite DO + hibernating WebSockets + R2 + Queues + persisted alarms, D1 только control plane. Остальное подключать по доказанной потребности. Развёрнутая и готовая принимать запросы система не должна поддерживать активный compute без работы.
